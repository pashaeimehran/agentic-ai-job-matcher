# Job–CV matching and ranking

## Contract and data flow

The structured job extractor remains backward compatible: `JobPosting.language`
stores names, not levels, and its historical 40-case extraction benchmark has
not been revised. `src/matching/requirements.py` converts these validated fields
into `JobRequirements`, optionally enriching explicitly evidenced CEFR levels
through a separate, quotation-checked LLM call. Curated test postings can supply
explicit levels without a paid call. There is no assumption that the old schema
already stores proficiency.

`ingested CV chunks -> cited CandidateFacts -> validated CandidateProfile`

`JobRequirements + CandidateProfile + hybrid retrieval -> Python score + comparisons`

`Comparisons + approved evidence -> optional LLM explanation -> source checks -> ranking`

The extractor reads stored chunks in bounded batches (at most 200 chunks and
10,000 characters per batch). It emits technical skills, languages and levels,
and employment records with explicit `YYYY-MM` start/end boundaries. Evidence
must cite an existing chunk and an exact substring; technical skill names,
language names and proficiency levels must also be visible in that quotation.

Live extraction may retry **once** if deterministic source validation fails.
For a skill already tied to a valid chunk ID and verbatim quotation, the
validator may re-anchor the quotation to source text that literally contains
the same skill. Fabricated chunk IDs or quotations are never silently repaired.
Employment periods with dates inferred from year-only evidence are excluded
before validation; unverifiable durations remain unknown. Invalid remaining
citations or unsupported claims still fail closed. These safeguards improve
source integrity but do **not** make LLM candidate-fact extraction fully reliable.
A source quote is not, by itself, proof that the LLM interpreted it correctly.

The demo fixture contains a *manually labeled* synthetic profile. It is not an
offline CV extractor and makes no claims about real-world extraction accuracy.
The live path uses the provider abstraction for sourced candidate extraction.

## Requirement comparison

For each explicit job skill, language and experience requirement, Python returns:

- `supported`: CV directly supports the requirement, or has an explicit level
  meeting the named language minimum.
- `unmet`: a clearly stated language level falls below the named minimum, or
  fully specified employment intervals total less than the requested years.
- `unknown`: no evidence, ambiguous level or incomplete employment boundaries.

An unmentioned skill is **unknown**, not explicitly missing. The finite skill
alias table avoids broad semantic equivalence guesses. Language levels use
A1 < A2 < B1 < B2 < C1 < C2 < native for the heuristic comparison. Native is
not a formal CEFR certificate. Language requirements without an explicit level
only require the language name to be evidenced.

A range such as `2023 to 2025` has unspecified months, so candidate employment
duration is *unknown*. An interval like `2023-02 to 2025-08` can be counted.
Months are counted using the union of all explicitly dated employment intervals;
overlapping jobs never increase calendar months twice. The existing posting
schema cannot reliably distinguish generic tenure from *role-specific relevant*
experience. Therefore this component is an approximate professional-tenure
comparison, **not a verified measure of relevant domain experience**. It must
not be used to make automated employment decisions.

## Deterministic score

| Component | Default raw weight | Evidence rule |
|---|---:|---|
| Skill overlap | 0.50 | Supported fraction of explicitly requested skills; unknown counts 0 |
| Employment duration | 0.20 | Supported=1, unmet=0, unknown=0.5 |
| Language match | 0.20 | Supported=1, unmet=0, unknown=0.5 |
| Retrieval similarity | 0.10 | Highest retrieved cosine, rescaled `(cosine+1)/2` |

If a posting lacks a component (e.g. no language requirements), that weight is
omitted and remaining weights are renormalized. Retrieval is included only
when the job has explicit requirements and cosine evidence is available. A
posting with no explicit requirements receives 0, not a forced semantic score.
The output is rounded to two decimals on a 0..100 *compatibility scale*. It is
not a hiring probability, confidence estimate or independent assessment of fit.
The response also reports how many explicit requirements were evidenced.

The original cosine is preserved as `retrieval_cosine`. The heuristic cosine
rescaling is not probabilistic calibration, and hash embeddings are merely a
lexical offline substitute. All scores, statuses, numerical contributions and
sort order are generated by Python; the LLM cannot modify them. Exact ties are
broken lexically by unique job ID.

## Retrieval, filtering and explanations

The prior pgvector cosine retrieval stays available and unchanged as a public
API. The new matching retrieval combines it with token-overlap retrieval via
reciprocal-rank fusion (RRF), then applies a deterministic token-coverage
rerank. Optional section metadata filters are passed into the SQL cosine query
and applied before lexical fusion. For this single-CV use case, `cv_id` is
also mandatory. This is not a learned reranker or a cross-encoder. The vector
candidate pool is capped at 500, and very large CVs are refused by profile
extraction rather than silently truncated.

Explanations use validated comparison objects and their approved original
source quotations. The optional LLM gets no permission to compute a score.
Python rejects invented requirement/status combinations, changed citation
IDs, altered quotations and unsupported positive/negative claims. Source
validation is syntactic; it does **not** guarantee that free-form explanation
text is semantically entailed. Ragas faithfulness testing remains important.
If no LLM explanation provider is supplied, a deterministic template is used.
`render_match_explanation()` then formats the deterministic comparisons and
approved claims as a job-specific summary, explicitly listing supported,
unmet, and unknown requirements. The `--explain` CLI flag prints this
presentation. Formatting does not recompute scores, rewrite requirement
statuses, or broaden the underlying evidence.

## Security and operational scope

This remains a local single-user CLI. CV-scoped queries are not authorization:
a web or multi-tenant interface needs authentication, authorization and PII
controls. Live candidate extraction and explanations send CV excerpts to
OpenAI. Do not publish results containing real candidate excerpts. The fixture
report contains only synthetic data. No existing Postgres schema migration is
required and no stored CV needs re-ingestion for the new read-only `list_chunks`
operation. Existing CV replacement, deletion and Docker volumes are unchanged.

## Evaluation boundaries and measured results

`python -m scripts.evaluate_job_matching` measures comparisons and lexical
retrieval on six hand-labeled synthetic job–CV pairs. Relevant evidence is
identified by matching a full expected quote in an expected source section.
Hit@3 counts one hit per job; precision@3 is relevant returned chunks divided
by returned chunks, and recall@3 is relevant returned chunks divided by all
labeled relevant chunks. The benchmark reports full denominators and both
vector-only and hybrid results. These are the *same* public development cases
used for implementation, not unseen real advertisements.

The offline labeled baseline achieved **25/25** correct status comparisons,
vector-only hash Hit@3 **5/6**, and hybrid hash Hit@3 **6/6**. Hash embeddings
are lexical substitutes and cannot establish performance of live semantic
retrieval for the same job queries.

The optional paid evaluator, `scripts.evaluate_matching_ragas.py`, separates
ranking from explanation generation: deterministic ranking runs first, and
LLM explanations are generated only for selected top-N jobs. Evaluator
contexts combine retrieved chunks with approved cited source chunks; Ragas
`Faithfulness` and `AnswerRelevancy` then evaluate the rendered summary.
`--profile-source extracted` exercises live candidate extraction, which may
intermittently fail strict source validation. `--profile-source labeled-fixture`
uses a human-labeled synthetic profile *only after* verifying that the stored
CV and chunks match the exact public fixture. This provides a more stable
explanation-quality benchmark but excludes candidate extraction accuracy.

The verified Windows three-job Ragas baseline on October 21, 2026, used
`--profile-source labeled-fixture`, with mean **faithfulness 0.7028** and
**answer relevancy 0.6980**. Job-level results and numeric JSON are recorded
in [the matching baseline](../benchmarks/matching_baseline.md). Results from
older one-job evaluations used different answer/context handling and should
not be presented as a controlled improvement. Ragas scores are variable
model-judge estimates, and source-linked claims may still be semantically
unfaithful. Faithfulness near 0.70 identifies a quality limitation to improve.

commands and the isolated Python 3.12 Ragas setup.
